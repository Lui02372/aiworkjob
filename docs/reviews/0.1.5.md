# impl-validator · 0.1.5

목표: 더 최신의 유효한 결제사 확인을 오래된 응답이 덮어써 취소 주문의 다운로드와 승인 합계를 되살리는 결함을 고친다.

| 확인 항목 | 판정 | 근거 |
|---|---|---|
| 실제 공개 패키지의 결함 재현 | PASS | v0.1.4 ZIP의 commerce.mjs와 수정 전 B가 동일 바이트다. 최초 회귀 4개 중 3개 실패, 취소 후 다운로드가 HTTP 200이었다. |
| 승인·주문 조회·다운로드·웹훅의 공통 처리 | PASS | 각 제공업체 요청 직전 SQLite 순번을 발급하고 recordPayment의 조건부 UPDATE로 마지막 유효 응답만 반영한다. 무효한 응답은 적용 순번을 갱신하지 않는다. |
| 취소 이후의 오래된 응답 | PASS | 늦은 승인 응답과 조회 응답은 현재 저장된 취소 영수증을 반환하고, 다운로드는 409이며 승인 합계는 0이다. |
| 여러 인스턴스·재시작 | PASS | 같은 임시 DB를 연 독립 createStore 인스턴스로 취소와 다운로드를 겹쳤다. DB에 순번과 취소가 보존된다. 서로 다른 주문은 차단하지 않는다. |
| 실패 응답·검증 불일치 | PASS | 뒤에 시작한 요청이 네트워크 오류 또는 금액 불일치로 실패해도 앞선 유효한 취소 확인을 반영한다. |
| 겹친 응답의 웹훅 검증 해시 | PASS | 승인과 겹친 조회 응답에 secret이 없으면 오래된 row의 null을 쓰지 않고 현재 DB 해시를 유지한다. 수정 전 정상 웹훅이 400이던 추가 회귀를 재현했고 수정 후 200이다. |
| 기존 사용자 데이터 | PASS | 공개된 이전 스키마에 영수증·토큰 해시·이전 상품·다운로드 횟수를 넣은 임시 DB를 이행했다. 원래 필드 전체가 같고, 기존 토큰으로 같은 상품 바이트를 내려받아 재시작 후 확인했다. |
| 권한·금액·멱등성 | PASS | 기존 판매 검사 14개를 유지한다. 새 외부 승인·취소 API나 실제 결제를 추가하지 않는다. |
| 코드 범위 | PASS | 소비 측 commerce와 검증·문서·버전만 변경했다. SDK·계정 관리자 소스·공용 승격 도구·원본 checkout은 변경하지 않는다. |

현재 구현 검토: PASS. 판매 Node 23개, 전체 Node 80개, 정적 웹 23개, 판매 화면 11개, 계정 관리자 화면 8개, 두 앱 HTTP 4개가 통과했다. API 36 emulator-5560의 업데이트 6개와 Android 실행 11개, 압축 해제 실행 7개도 통과했다. 모든 결제 응답과 모델은 주입한 모의 구현이며 실결제·실수익의 근거가 아니다. 검토는 impl-validator 프로토콜에 따른 자체 체크리스트이며 독립 에이전트 검토로 표시하지 않는다.

순번은 요청 시작 순서이며 결제사가 서명한 전역 이벤트 번호가 아니다. 확인 이후 외부에서 새로 발생한 취소를 미리 알 수는 없고, 기존 정책대로 매 다운로드 전에 결제사에 조회한다. 이 수정의 인스턴스 간 순번 보장은 동일 수정 버전을 쓰는 프로세스에 적용된다. 실행 중인 이전 A는 보존하며 새 A 소스는 다음 실행부터 적용한다. 실제 키·상점·라이브 결제·정산 연결은 여전히 필요하다.

실패·수정 근거: `artifacts/maintenance-2026-10-29-1701/commerce-race-before.txt`, `commerce-race-after.txt`, `baseline-release-code.json`. APK·업데이트·압축 해제·승격·공개 검증은 `docs/IMPROVEMENTS.md`와 같은 실행 폴더의 최종 게시 근거에서 확인한다.
